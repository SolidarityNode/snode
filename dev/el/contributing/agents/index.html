    AGENTS.md¶

    Instructions for every coding agent (Claude Code, Codex, Cursor and others) and every human contributor working in this repository. Area folders (core/, backend/, frontend/, data-processing/) have their own AGENTS.md with additional rules; read the one for the folder you work in. Human-readable explanations are in docs/conventions/.

    Project¶

    SolidarityNode is an open-source spatial probabilistic framework for estimating accessibility, latent social need, social vulnerability and resilience of social service networks (healthcare, social care and other public services). It uses Bayesian Networks (BN), Dynamic Bayesian Networks (DBN) and spatial/network analysis. It is research software in early development.

    Source of truth for the science: docs/specs/ (research description and per-module specs). If code and spec disagree, stop and flag it; do not silently pick one.

    Domain invariants (never violate)¶

    1. Unit of analysis is spatial unit × social group × service × time. Core data structures and outputs are indexed by these four dimensions.
    2. Vulnerability is not resilience, and not risk. Vulnerability is the relationship that turns a disruption (group exposure, service loss) into consequences for a group given its social susceptibility; in code it is the CPT P(V | GE, SL, SS), evaluated at scenarios (Paper 3) or at observed disruptions (Paper 4), and learned from data as parameters (OQ-16). Resilience = dynamic property derived from the loss-and-recovery trajectory. Risk = vulnerability weighted by disruption probabilities. Separate modules, separate outputs. Never define resilience as just the inverse of recovery time, and never let vulnerability results depend on which scenarios a run includes.
    3. Facility state is not population service loss. A degraded facility does not imply lost coverage for a spatial unit if alternatives exist. Coverage is computed at the network level.
    4. Observed demand is not need. Latent need is estimated explicitly; keep observed demand and estimated need as distinct quantities. Hidden need (never expressed), unmet expressed need (requests not fulfilled) and met need never overlap; take-up means expressing need, not being served (OQ-8).
    5. Social group is not social susceptibility. The group says who is being examined; susceptibility is the probability that the group faces increased difficulty under given conditions.
    6. Outputs carry uncertainty. Prefer distributions or intervals to point estimates. Never collapse uncertainty silently.
    7. Operational support is a system response, not an independent resilience measure.
    8. Digital Twin is a future direction, not an assumption. Do not build twin-specific machinery yet.
    9. Keep variable kinds distinct. BN nodes, computed simulation variables and scenario parameters are different things (see docs/specs/00-domain-model.md, section 4). Do not turn one into another without an ADR.
    10. Decisions feed the papers. When a ticket or ADR changes the method, update docs/specs/paper-revisions.md (what changes in which paper section, and why) in the same PR.
    11. Open questions are not yours to resolve. docs/specs/open-questions.md lists what the papers leave unspecified. Implement only what a spec states; reference OQ-n in code and tickets; if a ticket needs an unresolved answer, stop and comment on the issue.

    Architecture rules¶

    • Monorepo: core/ (Python library), backend/ (API), frontend/ (web UI), docs/, .github/.
    • Dependency direction: backend → core. core MUST NOT import from backend or frontend, and MUST NOT depend on web frameworks or a database driver.
    • core modules (map in docs/specs/00-domain-model.md): model, bayes, accessibility, demand, capacity, service_gap, latent_need, scenarios, vulnerability, operations, dynamics, resilience, uncertainty, sensitivity, validation. Each exposes a small typed public API; internals are private.
    • Long-running simulations run as background jobs, never inside a request handler.
    • Large datasets live in files (Parquet), metadata and results indexes in PostgreSQL/PostGIS.
    • Significant decisions are recorded as short ADRs in docs/adr/.

    Stack (initial choices; change via ADR)¶

    • Python 3.12, uv for environments, ruff (lint + format), mypy (strict in core), pytest.
    • Backend: FastAPI, Pydantic v2, SQLAlchemy + Alembic, PostgreSQL with PostGIS.
    • Core: NumPy, pandas, GeoPandas, NetworkX/OSMnx for network analysis, pgmpy (BN/DBN; evaluate limits via ADR before committing).
    • Frontend: React + TypeScript (strict), Vite, pnpm, Vitest, ESLint, Prettier, Playwright (end-to-end). Map library: Leaflet (ADR 0007).
    • Docs: MkDocs with the Material theme, versioned with mike, published to GitHub Pages (ADR 0018); tooling locked in tools/docs/.
    • Containers: Podman (rootless) is the default engine; Docker must keep working. The engine and compose command are set once in the Makefile (CONTAINER_ENGINE ?= podman, COMPOSE ?= podman compose) and are overridable from the environment. Never hard-code docker in scripts, docs or CI; call the Makefile variables instead. Compose files follow the Compose spec (compose.yaml) and images use fully qualified names (for example docker.io/postgis/postgis:...), since Podman requires them. Avoid privileged ports (<1024) and rootful-only features. Everything runs locally with make up.

    Commands¶

    Requires uv, Node.js 26 with pnpm 12, and Podman (or Docker). make help lists all targets.

    • make setup — check that uv, node and pnpm are on PATH (names any missing), create .env from .env.example if missing (warns about missing keys), then install locked dependencies (uv sync --locked in core/ and backend/, pnpm install --frozen-lockfile in frontend/)
    • make lint — ruff check, ruff format --check and mypy (strict) for core and backend; eslint, prettier --check and tsc for frontend; the platform version and the generated docs blocks are current; Greek docs pages exist for the user guide (stale ones are a warning)
    • make test — fast, no container engine: unit and integration tests only, pytest (core; backend on a throw-away database on an existing PostGIS server: the db service of make up or make test-db, or SOLIDARITYNODE_TEST_DATABASE_URL) and Vitest (frontend)
    • make test-e2e — the Playwright end-to-end test, also run in CI: a separate throw-away stack (compose project solidaritynode-e2e on ports 18080/18000/15432, seeded with demo package 1.0.0 and removed afterwards); Playwright runs in its official image, E2E_LOCAL=1 uses a host browser
    • make fmt — ruff fix/format, prettier, eslint --fix
    • make up / make down — start/stop db, backend, worker and frontend with $(COMPOSE) (default podman compose); frontend http://127.0.0.1:8080, backend http://127.0.0.1:8000; passes GIT_COMMIT to the image builds
    • make logs, make ps, make wait, make stop SERVICE=… — follow logs, show containers, wait until the backend is ready, stop one service (for example worker)
    • make db-shell — psql in the database container with the credentials from .env
    • make seed — import demo package 1.0.0 (no-op if present), create the demo users when APP_ENV=development, wait for queued runs
    • make import-package PKG=<dir or archive> — validate, preview and (after typing yes, or YES=1) import a data package
    • make activate-version VERSION=<x.y.z> — make an earlier imported data version active again (rollback; queues a baseline run, revalidates scenarios; asks for yes unless YES=1)
    • make create-admin — create the first administrator interactively
    • make schemas — export docs/schemas/scenario.schema.json and openapi.json, regenerate the frontend API types
    • make reset — delete the database and results volumes, start, migrate and seed; asks for yes unless FORCE=1
    • make uat — reset then up, then print the URLs and demo credentials (UAT: docs/uat/)
    • make env — create .env if missing and warn about missing keys
    • make check-config APP_ENV=production — validate backend settings in a one-off container (refuses change-me secrets outside development and test)
    • make images — build images with $(CONTAINER_ENGINE)
    • make licenses — fail on dependency licences incompatible with AGPL-3.0
    • make docs / make docs-build — serve the documentation site on http://127.0.0.1:8001 / build it with --strict (CI); make docs-links checks links with lychee
    • make docs-generate — regenerate the ADR index, the specs index and the open-question counts (never edit those blocks by hand)
    • make docs-stamp PAGE=docs/<page>.el.md — record that a Greek page matches its English source again (ADR 0019)
    • make deps-report — regenerate docs/architecture/dependencies.md from the lock files (after make setup); CI fails if it is stale or a licence is not allowed
    • make version / make version-sync — print the platform version / write VERSION into the manifests and locks (VERSION is the only place to change it; docs/releasing.md)
    • make labels — create GitHub labels from .github/labels.yml (needs gh auth login)
    • make clean / make distclean — remove caches and build output / also virtualenvs and node_modules
    • Per component: make lint-core, test-core, lint-backend, test-backend, lint-frontend, test-frontend
    • Docker instead of Podman: CONTAINER_ENGINE=docker COMPOSE="docker compose" make up
    • Regenerate the synthetic demo dataset: python3 scripts/generate_demo_data.py (update DP-001); rebuild the demo packages: python3 scripts/build_demo_packages.py (update DP-002)

    Run make lint test before every commit. Do not mark work done if either fails.

    Conventions¶

    • Type hints everywhere in Python; no untyped public functions.
    • Small, pure, testable functions in core. Randomness goes through an explicit seed/numpy.random.Generator argument.
    • Every public function in core has a docstring stating its inputs, outputs, units and the spec section it implements (for example Spec §3.1).
    • Tests live next to the code's package in tests/. Use synthetic fixtures only.
    • Commits: Conventional Commits (feat:, fix:, docs:, test:, refactor:, chore:), signed off with git commit -s (DCO).
    • Branches: feat/<issue-number>-short-name. One ticket, one branch, one PR. Reference the issue in the PR (Closes #N).

    Documentation rules¶

    • Diagrams in docs are Mermaid code blocks in the Markdown files (flowcharts for structure and data flow, sequence diagrams for lifecycles, state diagrams for statuses, entity-relationship diagrams for data models). No image files and no other diagram tools for diagrams. Update a diagram in the same PR as the change it describes.
    • Every PR that changes behaviour adds a line under Unreleased in CHANGELOG.md and updates the user guide page it affects (docs/user-guide/).
    • Do not copy what lives elsewhere; link to the single source: issues and plans in GitHub (project Kintsugi, milestones), open questions in docs/specs/open-questions.md, decisions in docs/adr/, method in docs/specs/.
    • Generated content (ADR index, specs index, open-question counts, docs/architecture/dependencies.md) comes from scripts and is checked in CI; never edit it by hand.
    • Do not move a file under docs/ that code, tests or AGENTS.md link to; change the site navigation in mkdocs.yml instead.
    • The user-facing pages (home, user guide, concepts, roadmap) have a Greek version page.el.md next to page.md (ADR 0019). When you change one of these English pages, update its Greek page (terms from docs/i18n/glossary.md, button names as in the Greek UI) and run make docs-stamp PAGE=<page>.el.md, or say in the PR that the Greek page is stale. make lint warns about stale Greek pages and fails if a user-guide page has no Greek version. Other pages stay in English; Greek pages mark links to them "(στα αγγλικά)".

    Data and privacy rules¶

    • Never commit real personal or operational data. Only synthetic data under core/tests/fixtures/ and data/synthetic/.
    • The request-logging mechanism must be anonymous by design: store only spatial unit of origin, social group, service type, the facility where the request is made or scheduled (OQ-29) and timestamps. No names, contact details, exact addresses or device identifiers. The facility raises re-identification risk in small units and follows the OQ-21 rules (minimum cell sizes, aggregation, retention); no ticket is stored until they are decided (ADR 0010).
    • No secrets in the repo. Use .env (gitignored) and keep .env.example current.
    • Configuration: the platform must run in development with no manual editing of .env. make setup creates .env from .env.example if missing and warns about keys present in .env.example but missing from .env. Every new setting is added to .env.example in the same PR, with a safe development default (secrets as change-me), a one-line comment, and an entry in the configuration section of CONTRIBUTING.md. Production values are never committed.
    • Third-party data (for example OpenStreetMap) must be attributed and its license respected; record sources in docs/data-sources.md.
    • Every processed dataset has a processing note in docs/data-processing/ (DP-NNN, from TEMPLATE.md), with exact steps, versions and checks. Reusable processing lives in data-processing/qgis/ (Processing models, scripts, projects with relative paths). When code or a ticket changes how data are prepared, update or add the note in the same PR. QGIS is a tool for preparing data, never a runtime dependency of core or backend.

    Licensing¶

    • Project license: AGPL-3.0. New dependencies must have AGPL-compatible licenses (MIT, BSD, Apache-2.0 are fine; no GPL-incompatible or proprietary-only dependencies). State the license of any new dependency in the PR description.

    Workflow for tickets¶

    1. Read the issue fully, including acceptance criteria and the linked spec section.
    2. If anything is ambiguous or the spec is silent, do not invent methodology: comment on the issue with the question and stop.
    3. Plan briefly, implement in small commits, add tests that cover each acceptance criterion.
    4. Update docs and the spec cross-reference if behaviour changed: the user guide page, a line under Unreleased in CHANGELOG.md, and Mermaid diagrams.
    5. Run make lint test (and make docs-build when docs changed), then open a PR using the template, assigned to the maintainer who asked for it (gh pr create --assignee <their-login>; see "Pull requests" in CONTRIBUTING.md). Do not merge your own PR.

    Every paper issue carries both the paper:N label and the Kintsugi Paper field with the same value (the label makes issue search links work; the field drives the project views), plus the paper's milestone (v0.3 Paper 1 Accessibility … v0.6 Paper 4 Resilience).

    Definition of done¶

    • All acceptance criteria met and covered by tests.
    • Lint, type check and tests pass locally and in CI.
    • Public API documented; relevant docs/ updated, including the user guide page and a CHANGELOG.md line under Unreleased when behaviour changed.
    • No real data, no secrets, no new dependency without a license check.
    • Domain invariants above still hold.

    Maintaining these instructions¶

    • Rules live in AGENTS.md files only. CLAUDE.md files are bridges (they import AGENTS.md) and never contain project rules. Do not create AGENT.md (singular) or other copies of the rules.
    • When asked to add, change or remove a rule:
    • Decide the area: root (applies everywhere), frontend, backend, core or data-processing.
    • If the rule can be enforced automatically (lint, type check, formatter, test, CI check), implement that instead or as well, and say so.
    • Check for conflicts or duplicates with existing rules in the root and area files; report them instead of silently overriding.
    • Edit the area AGENTS.md (short, imperative wording) and the matching docs/conventions/<area>.md (rule plus one-line reason and, if useful, an example). Root rules live in this file.
    • Do it on a branch docs/rule-<short-name> and open a PR titled docs(rules): <summary>, listing each rule added, changed or removed.
    • If a new area is needed (for example docs/ or .github/), create <folder>/AGENTS.md, its bridge <folder>/CLAUDE.md (containing only @AGENTS.md) and docs/conventions/<folder>.md in the same way.
    • Keep each area file short (under about 60 lines); move explanations to docs/conventions/.
